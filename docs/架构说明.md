# ProjectMentor 架构说明

> 本文档面向二次开发者，说明分层设计、数据模型与关键实现决策。
> 快速跑起来请看 [快速启动指南](快速启动指南.md)。

---

## 1. 分层架构

```
┌──────────────────────────────────────────────────────────┐
│  前端 React 18 + TS + Ant Design 5                        │
│  ┌────────────────────────┬─────────────────────────────┐ │
│  │ 主任务窗口（70%）       │ 答疑窗口（30%）              │ │
│  │ pages/ + components/   │ layout/ChatPanel.tsx        │ │
│  └────────────────────────┴─────────────────────────────┘ │
│           store/（Zustand：项目、当前任务、答疑消息）        │
│           api/（axios 封装，统一解包 {code,message,data}）  │
└───────────────────────────┬──────────────────────────────┘
                            │ HTTP /api/*
┌───────────────────────────▼──────────────────────────────┐
│  后端 FastAPI                                             │
│  api/        路由层：参数校验 + success() 包装，无业务逻辑  │
│  services/   业务层：领域路由、检索、LLM 编排、会话隔离      │
│  models/     ORM 层：SQLAlchemy 2.0 + SQLite              │
│  prompts/    Prompt 模板（与代码解耦）                      │
│  utils/      统一响应格式与全局异常处理                      │
└───────────────────────────┬──────────────────────────────┘
                            │
        ┌───────────────────┼───────────────────┐
        ▼                   ▼                   ▼
   DeepSeek API        GitHub REST API v3    SQLite
  (LangChain 封装)      (httpx 异步并发)
```

**分层约定**：路由层不写业务逻辑，业务逻辑不直接碰 HTTP 细节。
好处是 service 层可以脱离 FastAPI 单独测试，也便于替换实现
（例如把 GitHub 换成 GitLab 数据源，只需新增一个 service）。

## 2. 数据模型

统一项目模型：GitHub 开源项目与 AI 定制项目**共用同一张表**，用 `source` 区分。

```
projects ──1:N──> stages ──1:N──> tasks
   │                                │
   │                                └──1:1──> conversations (scope='task')
   ├──1:N──> conversations (scope='review')
   └──1:N──> reviews
                    │
                    └──1:N──> messages
```

### projects（项目）

| 字段 | 说明 |
| --- | --- |
| `name` / `source` / `domain` / `difficulty` | 基本信息，`source ∈ {github, custom}` |
| `status` | `learning` → `reviewing`（全部任务完成）→ `completed`（复盘完成） |
| `summary` / `background` / `goals` / `core_points` / `deliverables` | 内容字段，两种来源共用（`deliverables` 为列表，便于前端分点展示） |
| `target_audience` / `pitfalls` | 适配人群 / 常见学习误区 |
| `repo_url` / `repo_full_name` / `stars` / `language` | **GitHub 专有**，定制项目为空 |

`background` 对 GitHub 项目会追加 **README 摘要**（前 2000 字符），
让任务拆解与答疑能基于真实项目内容而不是仅凭仓库名猜测。

### stages（阶段）/ tasks（任务）

- 一个项目 4-6 个阶段，每阶段 3-5 个任务
- `tasks.order_index` 是**跨阶段连续**的全局序号，时间线与编号都依赖它
- `ddl_days` 是建议耗时；`due_date` 由服务层按顺序累加计算：
  `due_date(n) = 项目开始日 + Σ ddl_days(1..n)`
- `status ∈ {todo, in_progress, done}`，`started_at` / `completed_at` 随状态迁移维护

**关于任务顺序**：刻意**不设**顺序门禁。

早期实现里有一个 `Task.locked` property，要求前序任务全部完成后才能开始当前任务。
但真实的自主学习场景中，学习者可能已经掌握某部分内容、或想先看后面的任务再回头补，
硬性门禁会让人卡住。因此改为「推荐顺序、不强制」：

- 所有任务都可以直接开始
- 完成某个任务后，接口返回 `next_task` 作为推进建议（仅建议，不构成约束）
- 详情页与任务列表都不再展示锁定态

这样既保留了「按顺序推进」的产品引导，又不牺牲学习者的自主性。

### conversations（会话）/ messages（消息）

唯一约束 `(project_id, scope, task_id)` 是**双窗口隔离的基石**：

- `scope='task'` + `task_id` → 该任务独占一份会话
- `scope='review'` + `task_id=NULL` → 复盘答疑独占一份会话

因为约束在数据库层，每个任务天然只有一份独立会话，
切换任务时按 `(project_id, scope, task_id)` 查询即可拿到隔离的上下文，
不存在「会话串台」的可能。

### reviews（复盘）

`user_content` 保存用户原始输入，`final_content` 保存 AI 生成的文档，
`corrections` / `supplements` / `next_steps` 用 JSON 字段保存分项结果，
`structure_advice` 保存结构建议。同一项目只保留最新一次复盘。

## 3. 关键流程

### 3.1 项目匹配（双路径路由）

```
POST /api/project/match
  │
  ├─ 1. classify_domain()           LLM 判断技术类 / 通用类
  │      返回: category, search_keywords(英文), language, custom_hint
  │      （中文方向必须转成英文关键词，否则 GitHub 检索命中率极低）
  │
  ├─ 2a. 技术类 → match_github_projects()
  │      ├─ GitHub Search API: <keywords> stars:>500 pushed:>近一年 language:X
  │      │                       NOT awesome/tutorial/interview
  │      ├─ 并发校验 README 长度 ≥ 400 字符（过滤文档缺失的仓库）
  │      ├─ 候选不足时：放宽 language → 退回方向原文，逐级重试
  │      ├─ 优质项目 < 3 个 → 降级到 2b
  │      └─ LLM 逐条评估 → fit 分 → 按 (fit, stars) 排序取 Top 5
  │
  └─ 2b. 通用类 / 降级 → generate_custom_projects()
         LLM 生成 3 个小而实、有明确交付物的项目
```

### 3.2 开始学习（落库 + 拆解）

```
POST /api/project/start
  ├─ 创建 project 记录
  ├─ GitHub 项目 → 拉取 README 摘要追加到 background
  ├─ LLM 拆解 → stages[].tasks[]（含知识点、交付标准、ddl_days）
  └─ persist_decomposition() 写入并按序计算每个任务的 due_date
```

### 3.3 场景化答疑（上下文拼接）

每次提问都会重新拼接完整上下文，这是「精准不跑偏」的关键：

```
System Prompt = chat_answer.txt 模板
                └─ $context = build_project_context(project, task)
                   ├─ 项目基本信息（名称/来源/难度/简介/背景/目标/知识点/交付物/仓库）
                   ├─ 当前任务（所属阶段/名称/描述/知识点/交付标准/状态/DDL）
                   └─ 项目任务总览（★ 标记当前任务，让导师知道学习者的位置）

User Prompt  = 本任务最近 12 条历史对话 + 当前问题
```

历史对话只取最近 `_MAX_HISTORY_MESSAGES = 12` 条，避免上下文无限膨胀。

### 3.4 复盘

```
POST /api/review/generate
  ├─ 上下文 = 项目信息 + 用户复盘原文 + （若有）上次 AI 文档
  ├─ LLM 输出 JSON：corrections / supplements / structure_advice
  │                  / next_steps / final_document
  ├─ final_document 缺失时用 _fallback_document() 兜底拼装
  └─ 删除旧复盘记录 → 保存新记录 → 项目状态置为 completed
```

## 4. 设计决策记录

### 4.1 为什么用 `string.Template` 而不是 `str.format` 渲染 Prompt？

Prompt 里要写 JSON 输出示例，`str.format` 会把 `{` `}` 当占位符导致必须全部转义成 `{{` `}}`，
可读性极差。`string.Template` 用 `$var` 语法，模板中可以直接写原始 JSON。

### 4.2 为什么 LLM 调用要用 JSON 模式 + 本地容错解析？

模型偶尔会输出带 Markdown 代码块、尾逗号、或字符串内裸换行的"伪 JSON"。
`llm_service.extract_json()` 依次尝试：直接解析 → 剥离代码块 → 截取最外层括号
→ 修复尾逗号 → 转义裸控制字符，五重兜底后再失败才报错。

### 4.3 为什么 `max_tokens` 要开到 8192 / 16384？

`deepseek-flash` 是推理模型，`reasoning_content`（思考过程）与 `content`（正文）
**共享同一个 token 预算**。实测给 50 tokens 时全部被思考消耗、`content` 返回空字符串。
长文生成（复盘文档）单独使用 16384。

### 4.4 为什么把 rollup 换成 wasm 版本？

部分 macOS 环境下 Node 官方二进制启用了 Hardened Runtime（library validation），
而 rollup 的原生 addon 是 ad-hoc 签名，TeamID 不匹配会导致
`ERR_DLOPEN_FAILED: different Team IDs`。
`@rollup/wasm-node` 是官方等价替代实现，接口完全兼容，
通过 `frontend/pnpm-workspace.yaml` 的 `overrides` 声明。

### 4.5 为什么前端状态分成两个 store？

- `useAppStore`：跨页面共享的**项目与双窗口联动状态**（当前项目、当前任务、答疑消息）
- `useMatchStore`：**匹配流程的临时状态**（方向、难度、匹配结果）

拆开是因为匹配结果只服务于匹配页，且用户从匹配页返回首页再回来时不应丢失
（AI 匹配耗时 20-40 秒，重复调用体验很差）。生命周期不同，故分开管理。

## 5. 扩展指引

| 想做什么 | 改哪里 |
| --- | --- |
| 调整匹配/拆解/答疑的 Prompt | `backend/app/prompts/*.txt`（改完重启后端生效） |
| 换一个 LLM 提供商 | `backend/app/services/llm_service.py`（任何 OpenAI 兼容接口都可） |
| 调整 GitHub 筛选阈值 | `backend/.env` 的 `GITHUB_MIN_STARS` 等，或 `config.py` 默认值 |
| 新增数据源（如 GitLab） | 仿照 `github_service.py` 新增 service，在 `project_service` 中路由 |
| 调整双窗口比例 | `frontend/src/index.css` 的 `--pane-main-width` / `--pane-chat-width` |
| 新增任务类型字段 | `models/task.py` → `schemas/task.py` → `frontend/src/api/types.ts` 三处同步 |
